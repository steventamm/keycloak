# FedSetup Express Configuration in Keycloak: Architecture, Spec Validation, and Design Review

This document records the architecture, specification validation findings, extension recommendations, and comparative design analysis from implementing the FedSetup Express Configuration suite (`draft-tamm-express-configuration`, `draft-tamm-express-configuration-deferred-trust`, and `draft-tamm-express-configuration-extensions`) from first principles in Keycloak.

---

## 1. Design Decisions Made When Plugging FedSetup into Keycloak

### 1.1 Dedicated Top-Level Module (`fedsetup/services`) vs. Core `services/` Monolith

We structured FedSetup as a dedicated top-level Maven module (`fedsetup/pom.xml` and `fedsetup/services/pom.xml`, producing `org.keycloak:keycloak-fedsetup-services`), wired into the root `pom.xml` and `quarkus/runtime/pom.xml`. This follows the exact modularization pattern established by Keycloak's newer standards implementations—specifically `scim/` (`org.keycloak:keycloak-scim-services`), `ssf/` (`org.keycloak:keycloak-ssf-services`), and `authzen/` (`org.keycloak:keycloak-authzen-services`)—rather than adding dozens of classes into `services/` (`org.keycloak:keycloak-services`), which is already a legacy monolith containing over 1,500 classes.

Isolating FedSetup in `fedsetup/services` provides three concrete engineering benefits:

1. **Strict SPI Boundary Discipline:** `keycloak-fedsetup-services` depends only on `keycloak-core`, `keycloak-server-spi`, `keycloak-server-spi-private`, and `keycloak-services`, integrating exclusively through standard `META-INF/services` SPI registrations (`WellKnownProviderFactory`, `RealmResourceProviderFactory`, and `AdminRealmResourceProviderFactory`) without modifying existing OIDC, SAML, or SCIM classes.
2. **Independent Compilation and Fast Verification:** Developing and compiling `fedsetup/services` takes ~6 seconds in isolation without recompiling the entire `keycloak-services` module.
3. **Clean Packaging Optionality:** Quarkus runtime distributions can include or exclude the `keycloak-fedsetup-services` artifact as a self-contained feature unit.

### 1.2 Mapping Multi-Tenant Application Concepts to Keycloak Realms

A central goal of this implementation was validating how Express Configuration handles multi-tenant applications. In Keycloak, a **Realm** (`RealmModel`) is the fundamental unit of multi-tenancy: each realm has its own issuer URL (`/realms/{realm}`), signing keys (`session.keys()`), identity provider broker configurations (`realm.getIdentityProvidersStream()`), OAuth 2.0 / OIDC clients (`realm.getClientByClientId(...)`), and administrative permissions (`AdminAuth`).

We mapped FedSetup's tenancy model to Keycloak realms as follows:

- **Application Tenant Identifier (`application_tenant_id`):** Maps 1:1 to `realm.getName()`.
- **Multi-Tenant Default (`application_tenant_mode: "multi"`):** By default, a Keycloak deployment hosts multiple realms, so discovery advertises `"application_tenant_mode": "multi"`. Every signed Trust Establishment Authorization JWT, Front-Channel Consent request, and Signed Trust Pre-Authorization JWT must carry `application_tenant_id` matching the target `realm.getName()`. Mismatches after tenant resolution fail closed with `403 untrusted_issuer` without revealing whether another realm exists.
- **Single-Tenant Deployment Option (`application_tenant_mode: "single"`):** A single-realm Keycloak appliance can set the realm attribute `fedsetup.single_tenant_mode=true`. When enabled, discovery advertises `"application_tenant_mode": "single"` and `FedSetupJwtService` / `FedSetupService` accept requests that omit `application_tenant_id`, binding them automatically to `realm.getName()` while still rejecting any explicitly supplied `application_tenant_id` that does not match `realm.getName()`.

### 1.3 Discovery and Endpoint Routing via Keycloak SPIs

We registered three standard Keycloak SPIs in `META-INF/services`:

1. **`FedSetupWellKnownProviderFactory` (`org.keycloak.wellknown.WellKnownProviderFactory`, ID `fedsetup`):** Serves the Configuration Discovery Document (`/.well-known/fedsetup/realms/{realm}` and `/realms/{realm}/.well-known/fedsetup`). It dynamically advertises the realm's `application_base_uri`, `authorization_server`, `configuration_resource`, `configuration_endpoint`, `connection_endpoint_template`, `connection_query_endpoint`, `installation_endpoint`, `installation_consent_endpoint`, `installation_trust_jwks_uri`, `installation_trust_deferred_approval_supported: true`, `sso_connection_cardinality`, and the supported capabilities (`oidc`, `saml`, `scim`, `id_jag`, `connection_query`, `layered_updates`), Provider Delegation Profiles (`urn:ietf:params:fedsetup:config-delegate:ssf-stream`), and Federation Extension Profiles (`urn:ietf:params:fedsetup:config-ext:static-secret-delivery`, `urn:ietf:params:fedsetup:config-ext:scim-oauth-client-credentials`).
2. **`FedSetupRealmResourceProviderFactory` (`org.keycloak.services.resource.RealmResourceProviderFactory`, ID `fedsetup`):** Mounts `FedSetupResource` at `/realms/{realm}/fedsetup` with the following protocol endpoints:
   - `GET /realms/{realm}/fedsetup/consent` and `POST /realms/{realm}/fedsetup/consent`: Interactive Front-Channel Consent UI and decision handler (`{{trust-front-consent}}`).
   - `GET /realms/{realm}/fedsetup/trust-jwks`: Application public JWK Set (`application/jwk-set+json`) for verifying Signed Trust Pre-Authorization JWTs and Deferred Approval Notification JWTs (`{{preauth-jwks}}`).
   - `GET /realms/{realm}/fedsetup/oidc-jwks/{connection_id}`: Per-Connection Application public JWK Set when an OIDC Connection uses `token_endpoint_auth_method: "private_key_jwt"` (`{{sec-app-jwks}}`).
   - `POST /realms/{realm}/fedsetup/install`: Unified installation endpoint (`{{trust-back}}`, `{{trust-front-confirm}}`, `{{preauth}}`, `{{deferred}}`) handling Back-Channel atomic installations, Front-Channel `confirmation_code` redemptions, Signed Trust Pre-Authorization JWT installations, and bodyless Deferred Approval proposals and polls.
   - `POST /realms/{realm}/fedsetup/configure`: OAuth-authenticated Configuration Request endpoint for creating additional Connections under an established Direct Installation Trust (`{{config-syntax}}`).
   - `GET`, `PATCH`, `DELETE /realms/{realm}/fedsetup/connection/{connection_id}`: Connection retrieval, `If-Match` concurrency-controlled Layered Updates (including idempotent `scim.rotate_access_token`), and Connection deactivation (`{{update}}`, `{{revoke}}`).
   - `GET /realms/{realm}/fedsetup/connections`: Cursor-paginated Connection Query endpoint with `capability`, `status`, `limit`, and trust-bound `cursor` filtering (`{{query}}`).
3. **`FedSetupAdminRealmResourceProviderFactory` (`org.keycloak.services.resources.admin.ext.AdminRealmResourceProviderFactory`, ID `fedsetup`):** Mounts `FedSetupAdminResource` at `/admin/realms/{realm}/fedsetup`, protected by Keycloak's `AdminPermissionEvaluator`, providing REST endpoints for the Keycloak Admin Console UI (`overview`, `pending-authorizations`, `deferred-proposals`, `trusts`, `connections/adopt`, `connections/{id}`, `resource-bindings`, and `purge-keys`).

### 1.4 Storage and Cluster-Safe Replay/Idempotency State (`FedSetupStore`)

To avoid requiring custom Liquibase/JPA database schema migrations while remaining persistent across requests and cluster nodes, `FedSetupStore` partitions state into two native Keycloak storage layers:

- **Durable Realm Attributes (`RealmModel.setAttribute`):** Stores JSON-serialized records for `DirectInstallationTrustRecord` (`fedsetup.trust.{id}`), `PendingTrustAuthorizationRecord` (`fedsetup.preauth.{id}`), `DeferredApprovalProposalRecord` (`fedsetup.deferred.{pending_id}`), `ConnectionRecord` (`fedsetup.conn.{connection_id}`), and pre-authorized ID-JAG resource bindings (`fedsetup.resource_binding.all`).
- **Ephemeral Single-Use & Replay State (`SingleUseObjectProvider` via `session.singleUseObjects()`):** Uses Keycloak's cluster-aware Infinispan `SingleUseObjectProvider` for:
  - Single-use JWT `jti` replay prevention (`putIfAbsent("fedsetup.jti." + issuer + "." + jti, ttl)`).
  - Single-use Front-Channel `confirmation_code` issuance and atomic one-time consumption (`remove("fedsetup.code." + code)`).
  - Single-use Signed Trust Pre-Authorization JWT `jti` consumption and revocation tracking.
  - `Idempotency-Key` response caching keyed by `(authenticatedClientContext, operation, idempotencyKey)`, checked *before* consuming a `confirmation_code`, `trust_pre_authorization`, or `jti` so that network retries with a fresh outer JWT return the original `201 Created` or `200 OK` response without failing replay checks.

### 1.5 Provisioning Native Keycloak Federation Models (`FedSetupProvisioningService`)

When a Connection is created or updated, `FedSetupProvisioningService` translates the FedSetup capabilities into native Keycloak runtime objects:

- **OIDC (`oidc`):** Creates or updates an `OIDCIdentityProviderConfig` (`providerId = "oidc"`, `alias = "fedsetup-" + connectionId`), populating `issuer`, `authorizationUrl`, `tokenUrl`, `jwksUrl`, `userInfoUrl`, `logoutUrl`, `clientId`, write-only `clientSecret`, and `clientAuthMethod`, and returning the realm broker callback URI (`/realms/{realm}/broker/{alias}/endpoint`) in `oidc.redirect_uris` and `initiate_login_uri`.
- **SAML (`saml`):** Creates or updates a `SAMLIdentityProviderConfig` (`providerId = "saml"`), mapping `idp_entity_id`, `idp_sso_url`, `idp_slo_url`, `idp_certificate` (with signature validation enabled), and `nameid_format`, and returning `app_acs_url` and `app_entity_id`.
- **SCIM (`scim`):** Supports all three authentication modes:
  - `SAAS_ISSUED_BEARER`: Generates a high-entropy Connection-scoped bearer token on initial SCIM enablement or when `rotate_access_token: true` is sent on `PATCH`, storing only its SHA-256 hash and returning `Cache-Control: no-store` and `Pragma: no-cache`.
  - `STATIC_SECRET` (`urn:ietf:params:fedsetup:config-ext:static-secret-delivery`): Binds a connection-scoped `scim_authorization` secret hash and suppresses `scim.access_token`.
  - `OAUTH2_CLIENT_CREDENTIALS` (`urn:ietf:params:fedsetup:config-ext:scim-oauth-client-credentials`): Validates `scim_client_jwks_uri` (enforcing same-origin with `idp_issuer` and public-only JWKs), provisions a dedicated service-account `ClientModel` (`scim_client_{connection_id}`) configured with `client-jwt` and `jwks.url`, grants `realm-management` user/group roles (`manage-users`, `view-users`, `query-users`, `query-groups`), omits `scim.access_token`, and returns `token_endpoint`, `client_id`, `scope: "scim"`, and `resource` in `extensions["urn:ietf:params:fedsetup:config-ext:scim-oauth-client-credentials"]`.
- **ID-JAG (`id_jag`):** Validates `requester_type` (`app_instance` or `workload_principal`), `cimd_uri` or `client_secret` (enforcing distinctness from `oidc.client_secret`), and verifies every `resource_connections` entry (`resource_issuer`, `resources`, `scopes`) against the realm's pre-authorized resource bindings. It enables `jwtAuthorizationGrantEnabled` on the broker `IdentityProviderModel` and provisions the requesting `ClientModel` with `oauth2.jwt.authorization.grant.enabled=true`, `oauth2.jwt.authorization.grant.idp`, and `oauth2.jwt.authorization.grant.audience`.
- **SSF Stream Delegation (`urn:ietf:params:fedsetup:config-delegate:ssf-stream`):** Validates `transmitter_issuer` (must equal `idp_issuer`), `access_token`, and `events_requested`, persisting the stream delegation metadata for Keycloak's SSF receiver while redacting `provider_delegation` from `GET` responses.

### 1.6 User Interfaces (Front-Channel Consent UI & React Admin Console UI)

We implemented both user-facing surfaces required by an Application:

1. **Interactive Front-Channel Consent UI (`FedSetupService.renderConsentHtml`):** Served at `GET /realms/{realm}/fedsetup/consent`. Before rendering or redirecting anywhere, it fetches and validates the runtime's CIMD document and verifies `redirect_uri` by exact string comparison against `cimd.redirect_uris` (preventing open redirects). The UI displays the CIMD `client_name`/`logo_uri`, `idp_issuer`, target realm (`application_tenant_id`), and interactive checkboxes allowing the administrator to approve a downscoped subset of `authorized_capabilities`, `provider_delegation_profiles`, and `federation_extension_profiles`, protected with `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`.
2. **Keycloak Admin Console UI (`js/apps/admin-ui/src/identity-providers/FedSetupSection.tsx`):** Integrated as a **FedSetup Express Config** tab directly inside **Identity Providers** (`IdentityProvidersSection.tsx`), providing tables and modals for:
   - Viewing and deactivating active/deactivated FedSetup Connections and adopting existing manual `oidc`/`saml` Identity Providers (`Connection Adoption`).
   - Viewing and revoking active Direct Installation Trust records and purging cached CIMD/JWKS signing keys.
   - Creating Pending Trust Authorizations and generating/copying Signed Trust Pre-Authorization JWTs (`application/fedsetup-trust-preauth+jwt`) for out-of-band delivery to an IdP Tenant Admin.
   - Reviewing, downscoping/approving, or denying incoming Deferred Approval Proposals (`202 Accepted` queue).
   - Managing pre-authorized ID-JAG Resource Bindings (`resource_issuer`, `resources`, `scopes`).

## 2. What Was Missing from the FedSetup Spec That Had to Be Inferred

Implementing the three specifications from first principles against Keycloak surfaced several areas where normative behavior had to be inferred:

1. **Path-Prefixed Discovery URL Construction in Multi-Tenant Deployments (`{{disc-uri}}`):**
   - `draft-tamm-express-configuration` follows RFC 8615 by placing path suffixes *after* `/.well-known/fedsetup` (e.g., `https://keycloak.example.com/.well-known/fedsetup/realms/acme`). However, Keycloak's `WellKnownProvider` SPI (like many multi-tenant frameworks where the tenant is the first path segment) natively mounts well-known endpoints at `/realms/{realm}/.well-known/{alias}` unless a root-level reverse proxy or Quarkus route rewrite is added. Furthermore, when an IdP only knows the Application's base domain and the string `application_tenant_id: "acme"`, the spec does not define how the IdP knows whether the path prefix is `/realms/acme`, `/tenants/acme`, or `/o/acme` unless the IdP is given the full `application_base_uri` (`https://keycloak.example.com/realms/acme`). We supported both URL shapes in Keycloak, but the spec should clarify that in multi-tenant path-prefixed deployments, the IdP starts from the tenant's `application_base_uri` (or a discovery template) rather than guessing the path structure from `application_tenant_id`.
2. **Distinguishing Signed Trust Establishment Authorization JWTs from OAuth 2.0 Access Tokens on Dual-Auth Endpoints (`{{config-syntax}}`):**
   - `GET`, `PATCH`, and `DELETE` on `connection_endpoint_template` and `GET` on `connection_query_endpoint` accept *either* a signed Trust Establishment Authorization JWT (`{{auth-jwt}}`) or an OAuth 2.0 Bearer access token (`{{auth-oauth}}`) in the `Authorization: Bearer` header. Both are compact JWS strings (`eyJ...`). Because many authorization servers (including Keycloak) issue access tokens with header `typ: "JWT"` (the same `typ` used by Trust Establishment Authorization JWTs), a receiver cannot rely solely on the JWS header `typ` to distinguish them. We had to infer a discriminator rule: peeking at the unverified payload claims to check for the HTTP request-binding claims (`htm`, `htu`, `request_hash`) vs. OAuth access token claims (`azp`/`client_id`, `scope`, and `iss` matching the Application's `authorization_server`) before dispatching to the respective signature and scope validator.
3. **Bridging CIMD `client_id` Authentication to a Standard OAuth 2.0 Token Endpoint (`{{auth-oauth}}`):**
   - `{{auth-oauth}}` states that when OAuth 2.0 is advertised for the Configuration API, the IdP authenticates to `authorization_server` using `private_key_jwt` (or `tls_client_auth`) with `client_id` set to the installation runtime's CIMD URI. Standard OAuth 2.0 authorization servers look up a pre-registered client record by `client_id` at the token endpoint. The spec does not state whether the Application is expected to dynamically synthesize a local OAuth client registration in its AS when Direct Installation Trust is established (copying the CIMD's `jwks_uri` into the AS client record) or whether the AS itself must natively implement `draft-ietf-oauth-client-id-metadata-document` dynamic fetching during token requests. We inferred and implemented automatic provisioning of a Keycloak `ClientModel` (`clientId = cimdUri`, `clientAuthenticatorType = "client-jwt"`, `jwks.url = cimd.jwks_uri`) whenever Direct Installation Trust is created or revoked.
4. **Deferred Approval Poll Validation After Admin Downscoping (`{{deferred-poll}}`):**
   - In `draft-tamm-express-configuration-deferred-trust`, when an Application Tenant Admin approves a pending Deferred Approval proposal with a *subset* of the requested capabilities (downscoping), the IdP does not know the request was downscoped until it receives the `200 OK` poll response. Therefore, the IdP's poll JWT after approval still carries the *originally requested* `authorized_capabilities` array. Meanwhile, `{{deferred-poll}}` requires the Application to verify that a poll's scope matches the proposal's scope. We had to infer that a proposal record must separately store `requested_capabilities` (checked against incoming poll JWTs) and `approved_capabilities` (returned in the `200 OK` poll response and persisted into the `DirectInstallationTrustRecord`), rather than mutating a single capabilities field in place upon approval.
5. **Idempotency of Repeated `DELETE` Requests on a Deactivated Connection (`{{revoke}}`):**
   - `{{revoke}}` specifies that `DELETE {connection_endpoint_template}` returns `HTTP 204` and deactivates the Connection while retaining the record for audit purposes, and that a missing Connection returns `not_found` (`404`). However, `draft-tamm-express-configuration-extensions` (`{{query}}`) defines `"status": "deactivated"` as a queryable Connection state. We had to infer whether a retried `DELETE` on an already-deactivated Connection (which is not missing, since it appears in `GET /connections?status=deactivated`) should return `204 No Content` (following RFC 9110 idempotent `DELETE` semantics) or `404 not_found`. We implemented idempotent `204 No Content` for `DELETE` while returning `404 not_found` for `GET` and `PATCH` on a deactivated Connection.
6. **Discovery Advertisement of Pre-Authorized ID-JAG Resource Bindings (`{{idjag}}`):**
   - `{{idjag}}` requires the Application to reject any `id_jag.resource_connections` entry whose `resource_issuer`, `resources`, or `scopes` exceed a pre-authorized resource binding in the Application Tenant. However, neither the Discovery Document (`capabilities.id_jag`) nor the Deferred Approval / Consent responses carry the list of `resource_issuer` / `resources` / `scopes` that the Application Tenant has pre-authorized. We had to infer that the Application Tenant Admin configures these bindings in the Application UI and communicates them out of band (or that the IdP already knows the target resource server metadata).

## 3. Standard Federation Features That Should Be Included as Extensions

Validating the specification against Keycloak's full federation and authorization feature set highlighted five standard enterprise federation capabilities that should be added to the FedSetup extension suite:

### 3.1 OpenID AuthZEN Authorization API (`authzen` Capability or Provider Delegation Profile)

Keycloak natively implements the OpenID AuthZEN 1.0 specification (`authzen/services`, exposing `/.well-known/authzen-configuration` and `/realms/{realm}/authzen/access/v1/evaluation`, `evaluations`, `subject-search`, `resource-search`, and `action-search`). In modern enterprise architectures, SSO (`oidc`/`saml`), lifecycle provisioning (`scim`), and asynchronous security events (`ssf-stream`) are accompanied by **fine-grained externalized authorization (AuthZEN)**—either:

- **Application as PEP / IdP (or Enterprise Policy Server) as PDP:** The Application calls the enterprise tenant's AuthZEN Policy Decision Point (`access/v1/evaluation` or `evaluations`) to evaluate fine-grained access decisions or subject/resource searches.
- **IdP / AI Agent Gateway as PEP / Application as PDP:** An enterprise gateway or agent queries the Application's AuthZEN endpoint to determine whether a federated user or workload principal (`id_jag`) is authorized to perform an action on a resource before invoking an API or MCP tool.

**Proposed FedSetup Extension (`urn:ietf:params:fedsetup:config-delegate:authzen` or `authzen` capability):**

- **Discovery (`capabilities.authzen`):** Advertises the Application's AuthZEN role (`["pep", "pdp"]`), supported AuthZEN API versions (`["1.0"]`), supported endpoints (`evaluation`, `evaluations`, `subject_search`, `resource_search`, `action_search`), and supported client authentication mechanisms (`OAUTH2_CLIENT_CREDENTIALS`, `MTLS`, `BEARER`).
- **Configuration Request / Response:** Exchanges the PDP `policy_decision_point` issuer/discovery URI (`/.well-known/authzen-configuration`), entity-type mappings (how FedSetup/OIDC `sub` or SCIM `externalId` maps to AuthZEN `subject.type` and `subject.id`), and OAuth 2.0 client-credentials or bearer credential bindings (analogous to `scim-oauth-client-credentials` and `ssf-stream`).

### 3.2 OIDC Back-Channel Logout (OpenID Connect Back-Channel Logout 1.0 / RFC 8959)

In `draft-tamm-express-configuration` (`{{resp-ok}}`), the `oidc` response object returns `redirect_uris` and `post_logout_redirect_uris`, which only configure front-channel RP-Initiated Logout. Enterprise deployments almost universally require **OpenID Connect Back-Channel Logout** so that when an administrator revokes a user's session at the IdP (or the user logs out of another application), the IdP sends a signed `logout_token` JWT directly to the Application's back-channel logout endpoint.

- **Recommendation:** Add `backchannel_logout_uri` (OPTIONAL HTTPS URI) and `backchannel_logout_session_required` (OPTIONAL boolean) to the `oidc` response object in `{{resp-ok}}` (and corresponding metadata in the Application's CIMD document when the CIMD path is used). Keycloak's OIDC broker natively exposes a back-channel logout endpoint (`/realms/{realm}/protocol/openid-connect/ext/logout-channel` / broker logout endpoint) that can be populated automatically if these two fields are present in `{{resp-ok}}`.

### 3.3 Verified Email Domain / Home Realm Discovery (HRD) Routing (`idp_domains_verified`)

Keycloak 26+ includes a first-class **Organizations** feature (`org.keycloak.organization`) that maps verified email domains (e.g., `corp.example.com`, `subsidiary.example.com`) to a specific Identity Provider broker so users entering `alice@corp.example.com` are automatically routed to that IdP without clicking an IdP-specific button or using `initiate_login_uri`.

Currently, `draft-tamm-express-configuration` (`{{config-syntax}}`) defines `idp_domain` as a single display-only string and explicitly forbids using it as an authorization or routing binding because it is self-asserted.

- **Recommendation:** Define a Federation Extension Profile (e.g., `urn:ietf:params:fedsetup:config-ext:verified-domains`) or an array of domain bindings paired with DNS TXT / `.well-known` proof or Application Tenant Admin confirmation during Direct Installation Trust approval, allowing an Application to safely bind one or more email domains to the Connection for Home Realm Discovery.

### 3.4 SAML 2.0 Service Provider Signing & Encryption Metadata (`app_sp_certificate` / `app_metadata_url`)

In `{{saml}}` and `{{resp-ok}}`, the SAML request carries `idp_entity_id`, `idp_sso_url`, `idp_slo_url`, and `idp_certificate`, while the SAML response returns only `app_acs_url` and `app_entity_id`.

- **Recommendation:** Whenever `capabilities.saml.sp_initiated_slo_supported` is `true` (or when an IdP requires signed `AuthnRequest`s or encrypted assertions), the IdP needs the Application's SAML SP X.509 signing/encryption certificate (`app_signing_certificate`, `app_encryption_certificate`) or SAML SP Descriptor URL (`app_metadata_url`, which in Keycloak is `/realms/{realm}/broker/{alias}/endpoint/descriptor`). Adding `app_metadata_url` and `app_signing_certificate` to the `saml` response object in `{{resp-ok}}` eliminates manual certificate exchanges for SAML SLO and signed requests.

### 3.5 OAuth 2.0 Token Exchange (RFC 8693) Profiles Beyond ID-JAG

While `id_jag` covers cross-domain `jwt-bearer` exchanges using `oauth-id-jag+jwt`, Keycloak and enterprise API gateways also heavily use pure RFC 8693 Token Exchange (`urn:ietf:params:oauth:grant-type:token-exchange`) for on-behalf-of (`act` claim) service-to-service delegation within or across realms. Extending `id_jag` or registering a companion capability for RFC 8693 `token-exchange` policies (`subject_token_type`, `requested_token_type`, `actor_token_type`) would cover microservice meshes that do not mint separate `oauth-id-jag+jwt` assertions.

## 4. Compare and Contrast with the Existing `fedsetup-configuration` Branch

After completing and testing our implementation from first principles on the `express-configuration` branch, we inspected `remotes/origin/fedsetup-configuration` to compare architectural choices, specification alignment, and code structure.

| Dimension | First-Principles Implementation (`express-configuration`) | Previous Branch (`remotes/origin/fedsetup-configuration`) |
| --- | --- | --- |
| **Maven Module Placement** | Dedicated top-level module `fedsetup/services` (`org.keycloak:keycloak-fedsetup-services`), matching `scim/`, `ssf/`, and `authzen/`. Zero modifications to existing Java files in `services/` or `scim/`. | Placed 44 Java classes directly inside `services/src/main/java/org/keycloak/fedsetup/` and modified `AbstractOAuth2IdentityProvider`, `OIDCIdentityProvider`, `OIDCWellKnownProvider`, and `scim/services`. |
| **Protocol Role Scope** | Focused cleanly on the **Application Receiver** role across all three current drafts (`draft-tamm-express-configuration`, `draft-tamm-express-configuration-deferred-trust`, `draft-tamm-express-configuration-extensions`). | Implemented both **Application Receiver** and **IdP Outbound Dispatcher** (`OutboundInstallationDispatcher`, `OutboundTrustDispatcher`, `OutboundScimProvisioningDispatcher`, `FedSetupInstallationOutboxTask`, `FedSetupProvisioningEventListener`). |
| **Alignment with Current Endpoint Architecture** | Implements the current unified `installation_endpoint` (`POST /realms/{realm}/fedsetup/install`) that handles Back-Channel atomic installs, Front-Channel `confirmation_code` redemptions, Signed Pre-Auth JWTs, and bodyless Deferred Approval proposals/polls, plus `POST /configure` and `/connection/{connection_id}`. | Built against an earlier draft revision that separated `installation_trust_endpoint` (`/trust`), `installation_confirmation_endpoint` (`/front-channel/confirm`), and `configuration_endpoint` (`/connections`) into distinct URLs and used two-step trust-then-configure flows. |
| **OIDC Broker Provisioning** | Provisions standard Keycloak `OIDCIdentityProviderConfig` (`providerId = "oidc"`) and `SAMLIdentityProviderConfig` (`providerId = "saml"`), keeping broker behavior 100% compatible with standard Keycloak features. | Registered a custom `FedSetupOIDCIdentityProvider` (`providerId = "fedsetup-oidc"`) subclassing `OIDCIdentityProvider` to resolve AES-GCM encrypted `FedSetupCredentialReference` secrets and override `client_auth_method: none`. |
| **CIMD Client Authentication** | Provisions standard Keycloak `ClientModel` records (`client-jwt`) populated with the validated CIMD's `jwks_uri` and synchronizes lifecycle on trust revocation or key rotation. | Registered three custom `ClientAuthenticatorFactory` SPIs (`FedSetupConfigurationCimdClientAuthenticator`, `FedSetupScimCimdClientAuthenticator`, `FedSetupIdJagCimdClientAuthenticator`) that intercept `/protocol/openid-connect/token` requests. |
| **SCIM Authentication Modes** | Implements all three SCIM modes from the current specs: `SAAS_ISSUED_BEARER` (with idempotent `rotate_access_token`), `STATIC_SECRET` (`static-secret-delivery`), and `OAUTH2_CLIENT_CREDENTIALS` (`scim-oauth-client-credentials`). | Modified `scim/services` (`ScimRequestPermissionEvaluator`) to validate a single-use bootstrap bearer token and custom `FedSetupScimCimdClientAuthenticator` (did not implement `static-secret-delivery` or `ssf-stream`). |
| **Extension Coverage** | Implements all 6 capabilities/extensions in `draft-tamm-express-configuration-extensions`: `id_jag`, `connection_query`, `layered_updates`, `static-secret-delivery`, `scim-oauth-client-credentials`, and `ssf-stream`. | Implemented `id_jag`, `connection_query`, `layered_updates`, and SCIM OAuth client credentials; omitted `static-secret-delivery` and `ssf-stream`. |
| **Error Classification** | Uses strongly typed `FedSetupException` factory methods (`invalidRequest`, `invalidCredential`, `untrustedIssuer`, `insufficientScope`, `conflict`, `preconditionFailed`, `notFound`) tied directly to each validation step. | Used substring matching on exception messages in `FedSetupRealmResource.protocolErrorCode(status, message)` (e.g., `if (value.contains("pre-authorization") \|\| ...) return "untrusted_issuer"`). |
| **Admin Console UI Placement** | Added `FedSetupSection.tsx` as a top-level tab inside **Identity Providers** (`IdentityProvidersSection.tsx`), right alongside the OIDC/SAML brokers it manages and adopts. | Added `FedSetupTab.tsx` inside **Realm Settings** (`RealmSettingsTabs.tsx`). |

### Key Takeaways from the Comparison

1. **Value of Spec Simplification (Unified `installation_endpoint`):** Comparing `FedSetupService.java` in our implementation with `BackChannelTrustService.java` + `FrontChannelTrustService.java` + `FedSetupRealmResource.java` in `fedsetup-configuration` confirms that unifying atomic installation (`POST /install`) across Back-Channel, Front-Channel confirmation, Signed Pre-Auth JWT, and bodyless Deferred Approval substantially simplified the state machine and eliminated intermediate "trust established but no connection yet" race conditions for canonical flows.
2. **Trade-off Between Custom Authenticators vs. Native `ClientModel` Provisioning:** `fedsetup-configuration`'s custom `ClientAuthenticatorFactory` classes (`FedSetupConfigurationCimdClientAuthenticator`, etc.) allow live CIMD re-fetching on every `/token` call without storing `jwks.url` on a `ClientModel`, at the cost of invasive SPI hooks into Keycloak's OIDC token endpoint. Provisioning native `ClientModel` instances with `use.jwks.url=true` and `jwks.url=<cimd.jwks_uri>` (our approach) requires zero custom `ClientAuthenticator` code and works out of the box with Keycloak's existing `JWTClientAuthenticator`, provided the CIMD document itself supplies a `jwks_uri` (or the Admin Purge Keys action refreshes inline CIMD JWKs).

## 5. Comprehensive Review of the Keycloak Design Decisions in `dd/`

We reviewed all ten Keycloak-specific design decision records in `/Users/tamm/git/fedsetup/dd/` against both the current specification text and our implementation experience:

### 5.1 [Keycloak implementation of the IETF Direct Installation Trust profiles](file:///Users/tamm/git/fedsetup/dd/dd-keycloak-implementation-of-the-ietf-direct-installation-trust-profiles.md)
- **Summary:** Defines how Keycloak maps a realm to an Application Tenant, stores trust records in realm attributes, uses `SingleUseObjectProvider` for `jti` replay and confirmation codes, and exposes endpoints under `/realms/{realm}/fedsetup`.
- **Review & Spec Alignment:** The core storage decisions (realm attributes for low-volume configuration records + `SingleUseObjectProvider` for single-use `jti`/codes + realm signing keys for `/trust-jwks`) proved spot-on and were independently arrived at in our first-principles implementation. However, several protocol details in this DD reflect an earlier draft snapshot and are now out of date relative to `draft-tamm-express-configuration`:
  1. The DD describes separate `installation_trust_endpoint` (`/fedsetup/trust`), `installation_confirmation_endpoint` (`/fedsetup/front-channel/confirm`), and `configuration_endpoint` (`/fedsetup/connections`) endpoints where trust is established first and returns a `DirectInstallationTrust` JSON object (`201`/`200`), followed by a separate `POST /connections`. In the current spec, both canonical profiles are **atomic**: `POST /install` (`installation_endpoint`) establishes Direct Installation Trust *and* creates the Connection in a single transaction, returning the `201 Created` Connection response.
  2. The DD states that `urn:ietf:params:fedsetup:config-ext:scim-oauth-client-credentials` is not advertised; that was later superseded by `dd-keycloak-scim-core-bootstrap-and-renewal-extension.md`.

### 5.2 [Keycloak CIMD client sharing across Direct Installation Trusts](file:///Users/tamm/git/fedsetup/dd/dd-keycloak-cimd-client-sharing-across-direct-installation-trusts.md)
- **Summary:** Addresses a critical Keycloak data-model constraint: `RealmModel.addClient(clientId)` requires `client_id` to be unique per realm, whereas multiple IdP Tenants hosted by the same multi-tenant IdP Platform share the same installation runtime CIMD URI (`iss` / `client_id`), and therefore share the same OAuth `client_id` in one Keycloak realm.
- **Review & Spec Alignment:** This is an insightful and necessary design decision for any Application whose internal OAuth AS keys clients by `(realm, client_id)`. When two IdP Tenants (`https://tenant-a.idp.example.com` and `https://tenant-b.idp.example.com`) both use the runtime `https://runtime.idp.example.com/.well-known/oauth-client` to federate with the same Keycloak realm, a 1:1 `ClientModel` keyed by `client_id = cimd_uri` will collide on the second tenant unless either:
  1. One `ClientModel` (`client_id = cimd_uri`) is shared across trusts that use that CIMD URI and disambiguated by the `idp_issuer` claim or a per-trust client ID, or
  2. The Application provisions a synthetic per-trust `client_id` (or uses signed Trust Establishment Authorization JWTs, which carry `idp_issuer` in every token).
  - **Spec Improvement Opportunity:** `draft-tamm-express-configuration` (`{{auth-oauth}}`) assumes `client_id` at the Application's `authorization_server` is always the runtime's `cimd_uri`. When one multi-tenant IdP runtime manages Connections for *two different IdP Tenants* (`idp_issuer` A and `idp_issuer` B) inside the *same* Application Tenant, how does the IdP tell the Application's OAuth token endpoint *which* `idp_issuer`'s Direct Installation Trust it is requesting an access token for if `client_id`, `resource`, and `scope` are identical for both IdP Tenants? See Section 7.2 below—this DD uncovered a genuine protocol ambiguity in `{{auth-oauth}}`!

### 5.3 [Keycloak SCIM core bootstrap and renewal extension](file:///Users/tamm/git/fedsetup/dd/dd-keycloak-scim-core-bootstrap-and-renewal-extension.md)
- **Summary:** Models `SAAS_ISSUED_BEARER` as a single-use bootstrap token that is immediately invalidated once the IdP uses `urn:ietf:params:fedsetup:config-ext:scim-oauth-client-credentials`.
- **Review & Spec Alignment:** This DD's design contradicts the current text of `draft-tamm-express-configuration` (`{{scim}}`, `{{resp-ok}}`) and `draft-tamm-express-configuration-extensions` (`{{scim-oauth}}`). The current spec explicitly states:
  - *"A Connection uses at most one SCIM authentication mode, and an Application MUST reject a request that selects more than one mode"* (`{{scim}}` line 916).
  - *"A non-core SCIM authentication mechanism defines its own response representation and MUST NOT return a core `access_token`"* (`{{resp-ok}}` line 963, `{{scim-oauth-response}}` line 326).
  - Furthermore, core `SAAS_ISSUED_BEARER` tokens are *not* single-use bootstrap tokens in the spec; they are long-lived Connection-unique bearer tokens rotated via `PATCH` with `scim.rotate_access_token: true`. Our implementation follows the current spec strictly: when `scim-oauth-client-credentials` is active, `scim.access_token` and `scim.token_type` are omitted from the response; when core `SAAS_ISSUED_BEARER` is active, the token remains valid until rotated or the Connection is deactivated.

### 5.4 [Native SCIM permission bridge for a validated FedSetup connection](file:///Users/tamm/git/fedsetup/dd/dd-native-scim-permission-bridge-for-a-validated-fedsetup-connection.md)
- **Summary:** Modifies `scim/services` (`ScimRequestPermissionEvaluator`) so that a FedSetup SCIM service account or bearer token can authorize SCIM v2 `/Users` and `/Groups` calls without requiring fine-grained Admin Permissions V2 (`fgap-v2`) to be configured manually.
- **Review & Spec Alignment:** The problem identified by this DD is real: Keycloak's experimental `scim/services` module checks `AdminPermissionsSchema` (`fgap-v2`) on the caller. In our implementation, when `OAUTH2_CLIENT_CREDENTIALS` is provisioned (`FedSetupProvisioningService.provisionScimOAuthClient`), we grant the service-account user the standard `realm-management` roles (`manage-users`, `view-users`, `query-users`, `query-groups`), which keeps `fedsetup/services` decoupled from `scim/services`. If `SAAS_ISSUED_BEARER` or `STATIC_SECRET` opaque tokens are used directly against `/realms/{realm}/scim/v2`, a lightweight filter or evaluator bridge is indeed needed because Keycloak's SCIM endpoint expects a Keycloak JWT access token by default.

### 5.5 [Scoping FedSetup OIDC broker credential resolution and public client authentication](file:///Users/tamm/git/fedsetup/dd/dd-scoping-fedsetup-oidc-broker-credential-resolution-and-public-client-authentication.md)
- **Summary:** Introduces a dedicated `fedsetup-oidc` (`FedSetupOIDCIdentityProvider`) provider ID so that FedSetup's encrypted credential reference resolution and `token_endpoint_auth_method: "none"` behavior do not alter standard `oidc` identity providers.
- **Review & Spec Alignment:** Isolating custom runtime behavior to a dedicated provider subclass is good defensive practice *if* custom runtime behavior is required. However, Keycloak's built-in `OIDCIdentityProvider` already supports vault references (`${vault.ID}`), standard client authentication methods (`client_secret_basic`, `client_secret_post`, `client_secret_jwt`, `private_key_jwt`), and PKCE. Using the standard `"oidc"` provider ID (as our implementation does) has a major advantage in Keycloak: the standard Admin Console Identity Provider detail pages, mappers, and Organizations integrations recognize `"oidc"` out of the box without needing custom UI templates for `"fedsetup-oidc"`.

### 5.6 [Keycloak as an ID-JAG resource receiver](file:///Users/tamm/git/fedsetup/dd/dd-keycloak-as-an-id-jag-resource-receiver.md)
- **Summary:** Maps FedSetup's `id_jag` capability (`draft-tamm-express-configuration-extensions` `{{idjag}}`) onto Keycloak's `JWTAuthorizationGrant` feature (`Profile.Feature.IDENTITY_ASSERTION_JWT`), enabling `jwtAuthorizationGrantEnabled` on the broker IdP and configuring `oauth2.jwt.authorization.grant.*` attributes on the requesting `ClientModel`.
- **Review & Spec Alignment:** This mapping fits Keycloak's architecture cleanly and we used the same underlying Keycloak client attributes (`oauth2.jwt.authorization.grant.enabled`, `oauth2.jwt.authorization.grant.idp`, `oauth2.jwt.authorization.grant.audience`). One important nuance we noted: `draft-tamm-express-configuration-extensions` (`{{idjag}}`) allows `resource_connections` to be *omitted* (e.g., when registering an independent `workload_principal` client before binding resources, as in `{{ex-idjag-secret}}`), and requires the response to omit `resource_connections` when the request omitted it. Our `FedSetupProvisioningService.processIdJag` explicitly tracks `requestHadResourceConnections` to preserve this exact response rule.

### 5.7 [Manual broker adoption](file:///Users/tamm/git/fedsetup/dd/dd-manual-broker-adoption.md)

Both our implementation (`FedSetupService.adoptExistingIdentityProvider` + the "Adopt Existing IdP" modal in `FedSetupSection.tsx`) and `fedsetup-configuration` enforce the spec's core security invariant: adoption is never inferred from mutable metadata during an unconfirmed push; it requires explicit Application Tenant Admin action and makes the adopted Connection discoverable via `GET /connections` (`origin: "adopted"`).

## 6. Examples That Should Have Been in the Spec to Make Implementation Clearer

Adding the following five non-normative examples to the specification suite would eliminate the most common sources of implementer ambiguity:

1. **Multi-Tenant Path-Prefixed Discovery and Tenant Binding Example (`draft-tamm-express-configuration`):**
   - All current examples in `draft-tamm-express-configuration` use a root host `https://app.example.com` with `application_tenant_id: "acme-corp"`, without showing how `application_base_uri` looks when the tenant is path-prefixed (e.g., `https://app.example.com/realms/acme-corp` vs. `https://acme-corp.app.example.com`). Adding a concrete example of `GET /.well-known/fedsetup/realms/acme-corp` returning `"application_base_uri": "https://app.example.com/realms/acme-corp"` and `"application_tenant_mode": "multi"` would make path-based multi-tenancy crystal clear.
2. **Front-Channel Consent Downscoping Example (`draft-tamm-express-configuration` `{{trust-front-confirm}}`):**
   - `{{trust-front-confirm}}` contains a subtle normative rule: when the Application Tenant Admin approves only a *subset* of the capabilities requested in the Consent Request (e.g., the IdP requested `authorized_capabilities=oidc%20scim` and the admin approved only `oidc`), the IdP's subsequent `POST /install` JWT must still carry `authorized_capabilities: ["oidc", "scim"]` (matching what it originally requested in the Consent Request), while the Application creates the Connection and Trust for `["oidc"]` only. Showing this downscoped exchange in `{{trust-front-confirm}}`—including what happens if the POST body also included a `"scim"` object that the admin just deselected—would prevent a major implementation pitfall (see Section 7.1).
3. **Complete End-to-End Deferred Approval + Subsequent Atomic Installation Sequence (`draft-tamm-express-configuration-deferred-trust`):**
   - `draft-tamm-express-configuration-deferred-trust` shows the bodyless proposal (`202 Accepted`), the webhook notification JWT, and the approved poll response (`200 OK`, `"trust_established": true`), but stops before showing the subsequent complete-body `POST /install` (or `POST /configure`) that actually creates the Connection (`201 Created`). Showing the full 4-step sequence (Proposal -> Notification -> Poll `200 OK` -> Complete-Body Installation `201 Created`) would make it unmistakable that the `200 OK` poll response establishes only the Direct Installation Trust, not the Connection.
4. **OAuth 2.0 Client-Credentials Token Request Using a CIMD `client_id` (`draft-tamm-express-configuration` `{{auth-oauth}}`):**
   - `{{auth-oauth}}` describes how the IdP obtains an OAuth 2.0 access token from `authorization_server` using `private_key_jwt` and RFC 8707 `resource`, but includes no wire example. An example showing `POST /token` with `grant_type=client_credentials`, `resource=https://app.example.com/fedsetup`, `scope=fedsetup:config:oidc fedsetup:config:scim`, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, and the decoded `client_assertion` JWT claims (`iss` = `sub` = CIMD URI) would clarify both client authentication and multi-tenant scoping.
5. **SCIM Token Rotation Replay with `Idempotency-Key` (`draft-tamm-express-configuration` `{{scim}}` & `{{config-syntax}}`):**
   - `{{config-syntax}}` specifies a special rule for `PATCH` when `scim.rotate_access_token: true`: it requires an `Idempotency-Key` and requires the Application to check the idempotency cache *before* evaluating the `If-Match` ETag precondition so a lost rotation response can be recovered even after the ETag has advanced. A short 2-request wire example showing the initial `PATCH` (`ETag: "v1"` -> `"v2"`) and the retry (`If-Match: "v1"` with the same `Idempotency-Key` returning `200 OK` with `"v2"` and the rotated `access_token` instead of `412 Precondition Failed`) would highlight this critical ordering requirement.

## 7. Other Questions That Would Have Been Clearer If Addressed in the Spec

During implementation and testing, seven normative questions arose that the specifications should address explicitly:

1. **In Front-Channel Consent (`{{trust-front-confirm}}`), what happens if the Application Tenant Admin downscopes a capability that is present in the IdP's `POST /install` body, and how does the IdP learn the approved capability set?**
   - In `{{trust-front}}`, step 1 (Consent Request) only redirects back `?code=...&state=...`—it does *not* include the approved capabilities in the redirect query string. Then in step 4 (`POST /install`), the IdP sends the `confirmation_code` *together with the complete Configuration Request JSON body* (e.g., containing both `"oidc"` and `"scim"`). If the Application Tenant Admin unchecked `scim` on the consent screen (approving only `oidc`), what should the Application do when it receives `POST /install` containing both `"oidc"` and `"scim"` in the JSON body?
   - If the Application rejects the request with `400 invalid_request` (because `scim` is not in the approved capabilities), the single-use `confirmation_code` is invalidated on a failed confirmation attempt (`{{trust-front-response}}` line 599: *"MUST invalidate it on first use, on expiry, and on any failed confirmation attempt"*), forcing the entire browser consent flow to start over! Conversely, if the Application ignores/drops the unapproved `"scim"` object and provisions only `"oidc"`, that conflicts with `{{cap-core}}` line 756 (*"An Application MUST reject a request supplying a capability object the authorization does not name as `invalid_request`"*). Moreover, `{{resp-ok}}` does not define an `authorized_capabilities` member on the `201 Created` Connection response, yet `{{trust-front-confirm}}` line 647 says *"The IdP MUST compare the returned Connection, `application_tenant_id`, `idp_issuer`, and approved capability and profile sets with what it requested"*.
   - **Recommendation:** Explicitly add `authorized_capabilities`, `provider_delegation_profiles`, and `federation_extension_profiles` as optional/conditional members of the `201 Created` Configuration Response (`{{resp-ok}}`) when trust is established or downscoped on `POST /install`, and clarify whether an unapproved capability object in a Front-Channel `POST /install` body is omitted from provisioning (downscoped) or rejected.
2. **In OAuth 2.0 Configuration Requests (`{{auth-oauth}}`), how does the Authorization Server disambiguate which `idp_issuer` a multi-tenant IdP runtime is acting for?**
   - A cloud IdP Platform operates a single installation runtime (`iss` / `client_id` = `https://runtime.idp.example.com/.well-known/oauth-client`). Suppose two different customer IdP Tenants on that platform (`https://customer1.idp.example.com` and `https://customer2.idp.example.com`) both establish Direct Installation Trust with the same Application Tenant (`acme-corp`). Both trusts bind the same `cimd_uri` (`https://runtime.idp.example.com/.well-known/oauth-client`) and the same `configuration_resource` (`https://app.example.com/realms/acme-corp/fedsetup`). When the runtime later calls the Application's OAuth 2.0 `token_endpoint` with `grant_type=client_credentials`, `client_id=https://runtime.idp.example.com/.well-known/oauth-client`, and `resource=https://app.example.com/realms/acme-corp/fedsetup`, how does the Application's AS know whether the requested access token should be bound to `customer1` or `customer2`?
   - **Recommendation:** Either include `idp_issuer` in the `client_assertion` JWT claims (or as a token request parameter) during `{{auth-oauth}}`, or have the `201 Created` installation response return a trust-specific OAuth `client_id` when the Application's AS requires 1:1 client-to-trust binding.
3. **Does `validate_only: true` on `POST /install` preserve single-use `confirmation_code` and `trust_pre_authorization` artifacts?**
   - `draft-tamm-express-configuration` (`{{config-syntax}}`) states that when `validate_only` is `true`, the Application *"MUST NOT create or modify a Connection, issue or rotate a credential, or consume the POST Idempotency-Key"*. `draft-tamm-express-configuration-deferred-trust` (`{{preauth}}`) adds that `validate_only: true` must not consume a `trust_pre_authorization` JWT or its `jti`. However, `{{trust-front-confirm}}` in `draft-tamm-express-configuration` does not explicitly state that `validate_only: true` must not consume the single-use `confirmation_code` or the outer JWT's `jti`. Stating this explicitly in `{{trust-front-confirm}}` will prevent implementers from accidentally burning the single-use `confirmation_code` during a dry-run validation.
4. **Does `sso_connection_cardinality: "single"` restrict Connections that have no SSO capability (e.g., SCIM-only or ID-JAG-only Connections)?**
   - `{{disc-members}}` defines `sso_connection_cardinality: "single"` as *"at most one active SSO Connection for a given IdP Tenant issuer and Application Tenant"*, and `{{cap-core}}` notes that an installation can be approved for provisioning (`scim`) or `id_jag` while withholding SSO (`oidc`/`saml`). Clarifying in `{{update}}` that a Connection containing only non-SSO capabilities (`scim`, `id_jag`) does not count as an "active SSO Connection" under `sso_connection_cardinality: "single"` (while noting whether an IdP should prefer patching the existing Connection vs. creating a second non-SSO Connection) would avoid false `409 conflict` rejections.
5. **What is the interaction between `oidc.client_secret` and `urn:ietf:params:fedsetup:config-ext:static-secret-delivery`'s `configuration_secret` binding?**
   - `draft-tamm-express-configuration` (`{{oidc}}`) defines `oidc.client_secret` directly inside the `oidc` object, whereas `draft-tamm-express-configuration-extensions` (`{{static-secret}}` & `{{iana-value-bindings}}`) registers `configuration_secret` in `extensions["urn:ietf:params:fedsetup:config-ext:static-secret-delivery"].secrets`. The spec should clarify that `oidc.client_secret` is the canonical field for the OIDC client secret, while `static-secret-delivery` `configuration_secret` is only for Application-declared `installation_parameters` of type `secret` with binding `configuration_secret` (and must not be used as a duplicate channel for `oidc.client_secret` or `id_jag.client_secret`).
6. **Should `DELETE` on an already-deactivated Connection return `204 No Content` or `404 not_found`?**
   - As noted in Section 2.5, `{{revoke}}` recommends retaining deactivated Connection records for audit purposes, and `{{query}}` exposes `"status": "deactivated"` in `GET /connections`. Specifying whether a repeated `DELETE` on a retained, deactivated Connection returns `204 No Content` (idempotent `DELETE`) or `404 not_found` will ensure consistent retry behavior across implementations.
7. **In `urn:ietf:params:fedsetup:config-delegate:ssf-stream`, how does the Application discover the IdP's SSF Transmitter Configuration Endpoint when `transmitter_configuration_endpoint` is omitted?**
   - `{{ssf-stream-input}}` marks `transmitter_configuration_endpoint` as OPTIONAL and says: *"When absent, the Application discovers it from `transmitter_issuer` as [SSF] specifies"*. OpenID Shared Signals Framework (SSF 1.0) defines `/.well-known/sse-configuration` (with path insertion or suffix handling relative to the transmitter issuer). Explicitly citing the `/.well-known/sse-configuration` well-known suffix in `{{ssf-stream-input}}` would save implementers from confusing it with `/.well-known/openid-configuration`.
